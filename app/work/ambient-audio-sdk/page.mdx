<CaseSection n="01" title="Problem">
  Ambient AI assistance works by capturing audio in the browser while a
  clinician uses their real day-to-day tools - an EHR, a scheduling app, a
  page we host. That audio has to leave the browser, arrive intact at an
  ingestion backend, and be transcribed into a note the clinician can trust.
</CaseSection>

<CaseSection n="02" title="Constraints">
  The SDK ships into environments we don't control:

</CaseSection>

<CaseSection n="04" title="Architecture">
  Everything behind the public API runs inside the SDK's own runtime -
  capture, encode, buffering, and transport in a single Web Worker keeps the
  host thread free, while a Web Audio graph on the main thread is the only
  touchpoint with the microphone.
  <AmbientSystemDiagram />
  The reducer of the whole system is the session state machine. Hosts call
  **start()** and observe events; the machine decides what actually has to
  happen for audio to flow safely - acquiring capture, opening the socket,
  spooling to IndexedDB when the network is bad, and tearing everything down
  in the right order when the session ends.
</CaseSection>

<CaseSection n="05" title="Key engineering decisions">
  <CaseList
    marker="→"
    items={[
      'State, not callbacks. Every lifecycle transition is just data; the UI renders it, and recovery logic reacts to it. It is what made failure modes auditable instead of emergent.',
      'A worker owns the pipeline. Encoding and buffering never fight the host thread for frame budget - audio keeps flowing even while the EHR page is re-rendering.',
      'IndexedDB as the offline spool, not a "buffer in memory and hope". If a chunk was captured, it exists on disk until it is acknowledged.',
      'Resumable, idempotent uploads. Every chunk carries an offset and a key; a reconnect picks up where the last ack left off instead of re-sending from zero.',
      'Reconnect with jitter and backoff. Thundering-herd reconnects after an outage are a failure mode of their own.',
      'A screen for every state. The host always knows: capturing, streaming, degraded, offline, retrying - with the exact reason attached.',
    ]}
  />
</CaseSection>

<CaseSection n="06" title="Failure modes, designed for">
  <AmbientRecoveryDiagram />
  <CaseList
    items={[
      'Socket dropped mid-upload - the chunk is persisted first; the retry gate backs off (1s → 30s cap) and resumes from the last acknowledged offset, never from zero.',
      'Page backgrounded and timers throttled - the worker keeps buffering what it can, and the state machine marks the session degraded instead of silently dying.',
      'Chart-closing races - a host destroying a session is a first-class event, not an edge case; teardown is ordered so the final chunks still make it out.',
      'Partial acks - a chunk that is acked-but-not-stored triggers a re-connection that resumes, with duplicates dropped at the offset boundary.',
      'Duplicate data - idempotency keys make re-uploads safe without the backend needing a transactional retry model.',
    ]}
  />
</CaseSection>
